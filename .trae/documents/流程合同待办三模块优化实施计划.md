# 流程管理 / 合同管理 / 待办管理 三模块优化实施计划

> 依据：《流程管理、合同管理、待办管理全面评审报告》（2026-09-26，基于实际代码逐文件验证）
> 范围：backend（PHP/CodeIgniter 4）+ frontend（Vue 3 + AG Grid）+ 数据库脚本（backend/database/）
> 约束：所有改动遵循项目既有规范（中文注释、def_* 元数据驱动、JWT 认证、金额 Decimal、软删标识、提交前同步 D:\git\php-mis）

---

## 一、背景与目标

评审确认三模块构成"合同 → 流程 → 待办"联动闭环（ContractService → WorkflowService → TodoService UNION 聚合），元数据驱动与人工待办约定是亮点，但存在：

- **4 类 P0 阻断/高危缺陷**：eval 条件表达式 RCE 面、SUPERIOR 审批人硬编码 admin、approve 无事务并发重复推进、撤回后合同状态永久卡"审批中"、合同编号并发重号
- **多类 P1 一致性缺口**：路由业务类型不一致导致金额分级路由失效、合同无数据权限、审批意见双写、超时规则无消费者、待办负责人 FIND_IN_SET 不走索引
- **P2 体验差距**：无消息推送、无日历视图、版本无内容快照

**总目标**：批次一消除 P0（数据正确性 + 安全性达标），批次二补齐 P1（一致性与权限达标），批次三按需做 P2 体验增强；全程不破坏现有元数据驱动架构。

---

## 二、实施原则

1. **小步分批**：每项改动独立可回滚，独立 git 提交（后端/前端分别提交，互注关联 commit）
2. **先验证后切换**：涉及数据结构变更的项（编号 SP、负责人关联表、金额 DECIMAL）采用"双写过渡 → 验证 → 切换"三段式
3. **禁止臆造**：每项实施前执行"前置检查清单"，确认表结构与数据现状后再动手
4. **事务边界统一**：新增 `TransactionTrait`（CI4 transStart/transComplete 封装），多步写操作一律包裹；注意 Mcommon 请求级缓存与同一连接一致性（调用 SP 发号必须 `getDb()->query()` 直连）
5. **不新增自动待办**：所有优化遵循"待办人工创建"硬约定，超时/到期提醒仅产生 oa_message 消息，不自动生成 oa_todo

### A1 移除 eval 条件表达式，改用安全操作符匹配器

- **问题**：`WorkflowService::evaluateCondition()`（L634-662）将 `def_workflow_edge.条件表达式` 做 `${变量}` 替换后 `@eval()` 执行——表达式存于 DB，配置权限失守即 RCE。
- **改动方案**：
  1. 在 `WorkflowService` 中新增 `evaluateConditionSafe(array $rule, array $variables): bool`，完全复用 `WorkflowRoutingService::matchAll/matchSingle/applyOperator/castCompare/toNumber`（L137-277）的既有安全实现（比较运算白名单分发，无 eval）
  2. `def_workflow_edge` 增加列 `匹配条件`（JSON 格式，同 `def_workflow_routing.匹配条件`：`{"合同金额":{">=":1000000},"合同类型":"采购合同"}`）；`条件表达式` 列保留只读兼容一个版本后删除
  3. `findNextNode()`（L599-632）改读 `匹配条件` 列并调 `evaluateConditionSafe`；无 `匹配条件` 的边视为默认边
  4. 存量迁移：依据 P-4 结果，存量边数量小则提供转换脚本（`表达式 → JSON` 逐条人工确认后 UPDATE），数量为零则直接删列
  5. 前端 `WorkflowEdgeForm.vue` 的条件输入从"表达式文本框"改为"字段 + 操作符 + 值"结构化编辑器（字段下拉来自流程变量白名单）
- **涉及文件**：`app/Services/Workflow/WorkflowService.php`、`app/Services/Workflow/WorkflowRoutingService.php`（比较逻辑抽公共类 `WorkflowConditionMatcher` 供两处复用）、`frontend/src/views/workflow-manage/components/WorkflowEdgeForm.vue`
- **验证**：单测覆盖 `=,!=,>,>=,<,<=,in,between,like,isnull,notnull` 与类型归一（"1000000" vs 1000000）；e2e 验证"采购合同 ≥100万走三级审批"分支命中
- **预期收益**：消除 RCE 高危面；条件配置与路由配置语言统一，降低维护成本
- **依赖**：无

### A2 撤回后合同状态回置（修复合同永久卡"审批中"）

- **问题**：`WorkflowApi::withdraw` 只更新流程表，合同无回调 → `def_contract_master_new.合同状态` 停留"审批中"，而 `updateContract` 仅放行"草稿/已驳回"（L234），该合同无法编辑、无法重提，永久卡死。
- **改动方案**：
  1. `WorkflowService::withdraw()`（L439-486）增加校验：当前节点存在"已处理"任务时拒绝撤回（仅允许首节点未处理前撤回，语义对齐钉钉/飞书）
  2. `ContractApi` 新增 `withdraw()` 端点：校验发起人 → 调 `ContractService::withdrawApproval()`（内部：`workflowService->withdraw()` → 合同状态回置"草稿" → `recordVersion(变更说明='撤回审批')`）→ 整体事务包裹
  3. 前端合同页撤回按钮从 `/workflow/withdraw` 改调 `/contract/withdraw`；`/workflow/withdraw` 保留给无业务回调的通用场景并在响应中提示
  4. B5 实施时将本方案的"合同域端点"模式抽象为业务回调注册表
- **涉及文件**：`app/Services/Workflow/WorkflowService.php`、`app/Controllers/ContractApi.php`、`app/Services/Contract/ContractService.php`、`frontend/src/store/modules/contract/index.ts`
- **验证**：e2e 全链路——创建合同 → 提交 → 首节点已审批后撤回被拒；首节点未审批撤回成功 → 合同状态="草稿" → 可修改 → 可重新提交
- **预期收益**：合同生命周期闭环恢复，消除生产级功能阻断
- **依赖**：A3（事务基础）

### A3 approve/startProcess 事务化 + 并发抢占

- **问题**：`approve()`（L128-255）无事务无锁：或签（OR）下两审批人并发 → 双双通过 `checkNodeApproved` → `createTasksForNode` 执行两次，下一节点任务重复生成；拒绝与同意竞态；`startProcess`（L82-117）实例插入与任务生成同样裸奔。
- **改动方案**：
  1. 新增 `TransactionTrait`：`withTransaction(callable $fn)` 封装 `transStart/transComplete/transRollback`，后续所有多步写复用
  2. 任务抢占：同意/拒绝处理时将任务更新改为条件更新——
     ```sql
     update def_workflow_task set 任务状态='已处理',处理结果=?,...
     where GUID=? and 任务状态='待处理'
     ```
     affected rows=0 时抛"任务已被处理或撤回"，杜绝同一任务被处理两次
  3. `approve()` 全流程（任务更新 → addTaskLog → 实例状态更新 → 下一节点任务生成）纳入同一事务
  4. `startProcess()`（实例插入 + 首节点任务生成）纳入事务
  5. `withdraw()` 同步纳入（依赖 A2 顺序）
  6. 注意：`Mcommon` 若存在连接级差异，事务内所有写必须走同一 `db_connect('btdc')` 连接实例
- **涉及文件**：`app/Services/Workflow/WorkflowService.php`、新增 `app/Traits/TransactionTrait.php`
- **验证**：并发单测（两请求同时 approve 同一 OR 节点不同任务，断言下一节点任务恰好生成一轮）；拒绝+同意并发，断言实例状态唯一
- **预期收益**：审批数据正确性质变；为 B2/B5 的事务边界打基础
- **依赖**：无

### A4 CC 节点改为非阻塞 + 已读端点

- **问题**：CC 任务以状态"待处理"写入 `def_workflow_task`（L544-566），而 `checkNodeApproved`（L826-874）统计节点全部任务 → CC 节点在 OR（同意数永远 0）与 AND（待处理数永远 >0）下均无法完成，**配置抄送即挂起实例**。设计文档中的 `def_workflow_cc` 表代码从未使用。
- **改动方案**：
  1. `checkNodeApproved` 统计 SQL 增加条件 `and 任务类型='APPROVAL'`（CC 任务不计入推进判定）
  2. 推进逻辑改造：`createTasksForNode` 遇节点类型='CC' 时仅生成任务后**立即返回继续推进信号**，由调用方（startProcess/approve）循环 `findNextNode` 直到落到审批/END 节点（抄送不阻塞，对齐主流语义）
  3. `WorkflowApi` 新增 `ackCc` 端点：将 CC 任务置"已处理/处理结果='已读'"并写 task_log，前端待办中心对来源=工作流的 CC 行提供"已读"按钮
  4. CC 任务不进入 `getPendingTasks` 的审批待办 UNION（或在待办中心单独分组展示）
- **涉及文件**：`app/Services/Workflow/WorkflowService.php`、`app/Controllers/WorkflowApi.php`、`frontend/src/views/oa-todo-center/index.vue`
- **验证**：e2e——流程 A →(CC 节点)→ B：提交后 CC 人收到任务且 B 审批人任务同时生成，A 节点审批后流程直接落到 B 无需 CC 人操作
- **预期收益**：抄送能力从"配置即卡死"变为可用
- **依赖**：A3

### A5 SUPERIOR 审批人真实实现

- **问题**：`getApproversBySuperior()`（L771-794）无视发起人，硬编码返回 `admin/'系统管理员'`——任何"直属上级"节点全部流到 admin，审批链路错误。
- **改动方案**（依据 P-3 检查结果二选一）：
  - **方案 A（推荐）**：`def_dept` 增加 `部门负责人` 字段（若无）→ 解析逻辑：发起人 `def_user.员工部门编码` → 查部门负责人工号 → 校验其在职有效；1010 部门管理页面（def_query_column 驱动）补负责人列维护
  - **方案 B**：`def_user` 增加 `直属上级工号` 字段，逐人维护
  - 兜底：解析不到负责人时**抛业务异常**（提示维护负责人），禁止静默回落 admin
- **涉及文件**：`app/Services/Workflow/WorkflowService.php`、DDL（def_dept 或 def_user）、`backend/database/` 增补脚本
- **验证**：单测覆盖"有负责人/无负责人抛异常/负责人离职"三态；e2e 验证发起人部门负责人收到审批任务
- **预期收益**：审批链路组织语义正确，摆脱 admin 单点
- **依赖**：P-3

### A6 合同编号改 SP 发号（防并发重号）

- **问题**：`generateContractNo()`（ContractService L576-598）`select max+1` 模式无锁，并发创建重号；项目在候选人编码上已有成熟的 `def_seq` 分桶 + `LAST_INSERT_ID` 防并发方案却未复用。
- **改动方案**：
  1. 仿 `sp_生成候选人编码` 新建 `sp_生成合同编号`：`def_seq` 增加 `合同编号-HTYYYYMMDD` 序列行，存储过程内 `update def_seq ...; select LAST_INSERT_ID()` 取号
  2. `ContractService::generateContractNo()` 改为调用 SP——**必须 `getDb()->query('call sp_生成合同编号()')` 直连**（Mcommon::select 有请求级缓存会导致重号，项目已有教训）
  3. 存量主表执行一次去重核查脚本；随后加活跃唯一索引：
     ```sql
     ALTER TABLE def_contract_master_new
       ADD UNIQUE KEY uk_合同编号_活跃 (合同编号, 删除标识, 有效标识);
     ```
     注意：与候选人编码约束同款前置——若历史软删行删除标识取值非 0/1 混用需先归一（项目 memory：为添加唯一约束需将无效行编码置 NULL 的同类操作）
  4. `backend/database/` 新增 `contract_no_seq_sp.sql` 记录 SP 与序列初始化
- **涉及文件**：`app/Services/Contract/ContractService.php`、新增 SP 脚本
- **验证**：并发 50 请求建合同，断言编号连续无重号
- **预期收益**：主数据完整性；对齐项目统一发号体系
- **依赖**：无

### A7 路由业务类型与匹配值统一（金额分级路由生效）

  4. 补集成测试：采购合同金额≥100万 → 断言命中 `contract_purchase_high_approval` 而非兜底
- **涉及文件**：`app/Services/Contract/ContractService.php`、`app/Services/Workflow/WorkflowService.php`、`backend/database/workflow_routing_examples.sql`、新增常量类
- **验证**：集成测试三条路由（高额/普通/销售）全部命中；生产路由配置核对报告
- **预期收益**：金额分级审批真正生效（这是路由体系存在的意义）

## 五、批次二：P1 完善性改进（10 项）

### B1 合同列表/详情接入部门数据权限

- **问题**：`ContractService::getList`（L30-96）仅按入参过滤，任何登录用户可翻全部合同——金额、甲乙方信息全员可见。
- **方案**：`ContractApi::list` 从 `userContext` 取 `deptCodeAuthz`（JWT 部门授权，项目既有机制）传入 `getList`：有授权部门 → `所属部门 in (授权部门)`；无授权标签 → 仅 `创建人=当前工号`；具备合同管理角色（view_role 聚合，参照导入授权=1 的做法）→ 全量。`detail` 同步校验可见性。
- **文件**：`ContractApi.php`、`ContractService.php`
- **收益**：合同敏感信息合规；复用既有权限体系，成本低。

### B2 handleApproval 事务化（消除双写不一致窗口）

- **问题**：`handleApproval`（L411-488）四步写（approve 内部多表 → 意见表插入 → 合同状态更新）跨服务无事务。
- **方案**：`WorkflowService::approve` 拆出 `approveInTransaction()`（不含事务，供组合）；`ContractService::handleApproval` 用 `TransactionTrait` 统一包裹：approve + opinion 插入 + 合同状态更新。B5 通用端点复用同一组合模式。
- **依赖**：A3
- **收益**：审批意见与流程状态不再出现"推进了但意见丢失"。

### B3 合同金额 DECIMAL 化 + 精确比较

- **问题**：金额 `quote()` 直接入库（L192）类型未约束；路由 `toNumber` 转 float 比较（WorkflowRoutingService L271-277）——违反项目"金额必须字符串/Decimal"硬约束，亿级金额有精度风险。
- **方案**：① `ALTER TABLE def_contract_master_new MODIFY 合同金额 DECIMAL(18,2)`（先核查存量非数值行）；② `createContract/updateContract` 入参校验 `is_numeric` 并规范化两位小数（字符串传递）；③ `WorkflowConditionMatcher` 金额比较改 `bccomp`（或以字符串×100 转整型比较）。
- **文件**：DDL 脚本、`ContractService.php`、匹配器类
- **收益**：满足财务硬约束，消除分级路由的精度错判。

### B4 流程超时规则消费者（先 NOTIFY，不做自动审批）

- **问题**：`超时天数/超时处理` 仅在 WorkflowApi CRUD 写入（L621-633/L151-153），全库无调度消费——配置形同虚设。
- **方案**：新增 `app/Services/Workflow/WorkflowRemindService::scanTimeout()`（参照 `TodoService::scanReminders` L1077 幂等模式）：扫 `def_workflow_task` 待处理 + 节点超时天数 → 按策略仅实现 `NOTIFY`（写 oa_message 到审批人 + task_log），**暂不实现自动同意**（AUTO_APPROVE 需业务确认后单独立项）；调度入口见 B10。
- **依赖**：B10
- **收益**：超时配置生效；审批停滞有感知。

### B5 通用审批端点 + 业务回调注册表

- **问题**：`WorkflowApi` 无 `/workflow/approve` 端点，审批逻辑只存在于 `ContractApi::approve`——其他业务接入必须复制 handleApproval。
- **方案**：① `WorkflowApi::approve`：校验任务 → 事务内 `approveInTransaction` → 按实例 `业务类型` 查回调注册表（`app/Config/WorkflowCallbacks.php`：`'合同' => [ContractWorkflowHandler::class, 'onTaskProcessed']`）执行业务回写；② 合同侧改薄：`ContractApi::approve` 复用通用逻辑，意见存储见 B6；③ 撤回回调（A2）迁入注册表统一维护。
- **依赖**：A2、A3、B2
- **收益**：流程引擎与业务解耦完成，面试/培训等后续业务接入成本降为一项回调实现。

### B6 消除审批意见双写

- **问题**：`def_contract_approval_opinion`（handleApproval L446-462）与 `def_workflow_task_log` 重复存储审批意见，两处可能不一致。
- **方案**：确立 `def_workflow_task_log` 为唯一事实源：合同审批意见查询改从 task_log 聚合（ContractFlowTimeline 数据源不变）；`handleApproval` 停写 opinion 表；观察一个版本后归档该表。
- **依赖**：B5
- **收益**：单一事实源，维护成本减半。

### B7 流程定义版本号修正

- **问题**：`definitionCreate`（WorkflowApi L137-146）版本号 `count(*)+1`，逻辑删除旧版本后与现存版本号冲突，`startProcess` 按"版本号 desc limit 1"取定义时行为不可预期。
- **方案**：改 `coalesce(max(版本号),0)+1`（同码）；并加 `unique(流程编码,版本号,删除标识)` 活跃唯一约束。
- **文件**：`WorkflowApi.php` + DDL
- **收益**：多版本启用互斥语义严谨化。

### B8 待办负责人关联表（FIND_IN_SET 索引失效治理）

- **问题**：`oa_todo.负责人` 逗号多值 + `FIND_IN_SET` 查询（TodoService L96）——违反 1NF 且无法命中 `idx_负责人`，数据量增长后待办中心全表扫描。
- **方案**（三段式）：
  1. 新表 `oa_todo_assignee(待办GUID, 工号, 角色类型[负责人/指派人])` + `key(工号, 角色类型)`；DDL 落 backend/database
  2. **双写过渡**：`createTodo/updateTodo/reassign` 写 `oa_todo` 同步维护关联表（存量跑一次回填脚本）
  3. **切换**：`getCenterData/getStats` 查询改 join 关联表 → 并行运行对账脚本（两路径结果 diff）→ 无差异后删除 FIND_IN_SET 路径；`oa_todo.负责人` 列保留只读一个版本后清理
- **文件**：`TodoService.php`、新增 DDL/回填脚本
- **收益**：待办中心查询复杂度量级从全表扫描降为索引击中；多负责人语义显式化。
- **依赖**：无

### B9 3020 通用工作台对 oa_todo 写保护

- **问题**：3020 待办事项走通用工作台 `def_query_config` 注册，通用 CRUD（RecordEditService 直接 SQL）可绕过 TodoService 状态机——不产生 oa_message 通知与 oa_todo_log 流水。
- **方案**：3020 的 def_query_config 增加只读标识（或 def_query_column 可编辑列为空）→ 通用工作台对该功能码隐藏行内编辑/新增/删除入口，写操作统一引导至 3030 待办中心/专用 API；若管理端确需表级维护，另行配一个受控的管理功能码。
- **文件**：`backend/database`（def_query_config 更新脚本）、`generic-query-workbench.vue` 只读模式支持
- **收益**：状态机、通知、流水三条约束不被绕过。

### B10 调度机制统一为 spark command

- **问题**：`remind-cron` 以 HTTP 端点暴露——鉴权未确认（P-5）：走 JWT 则外部 crontab 无法调用，豁免则任何人可触发（幂等故危害有限但不可审计）。
- **方案**：新增 `php spark todo:scan`（包装 `scanReminders`）与 `php spark workflow:timeout`（B4）；Windows 任务计划/Linux crontab 调用，日志落 `logs/`；`remind-cron` HTTP 端点加内部 token 校验后保留（或下线）。
- **收益**：调度可控、可审计、可观测（成功/失败日志）。
- **依赖**：P-5、B4

### B11 completeTodo 与周期生成事务化 + 幂等

- **问题**：`completeTodo → createNextPeriod` 两步无事务，中断/并发可能重复生成下一期。
- **方案**：TransactionTrait 包裹；`createNextPeriod` 增加幂等键：同任务链（父GUID 根）+ 同周期基准日已存在未完成子任务则跳过。
- **文件**：`TodoService.php`
- **收益**：周期任务不重发、不漏发。
